# This project

This repository's own instructions: its conventions, the commands that build and test it, the domain it serves, and any standing tasks or prompts that belong to this project and no other. `CLAUDE.md` loads this file and every session reads it after the kit's rules.

The project-process kit writes this file once and never touches it again, and `CLAUDE.md` is the kit's, replaced whole every time the bootstrap runs, so anything written there is lost. Write here instead. Where this file and the kit disagree about this project, this file wins, except that nothing here lifts the branch rule: the work still happens on a branch and ends as a pull request.

## Migrations run when their pull request merges

The `run migrations` workflow (`.github/workflows/run-migrations.yml`, calling `scripts/run-added-migrations.sh`) runs on every push to main. It runs every `migrations/*.sql` file on main that is **not yet on the record of applied migrations** (`public.applied_migrations`, 0197), in filename order, against the live Supabase database, each in a single transaction with `ON_ERROR_STOP`, as `scripts/run-migration.sh` does by hand, and records each file as it is applied: its name, when, the commit and a fingerprint of its contents. The record is written in the same transaction as the file, before its contents, because most files end with their own `commit`, which commits psql's single transaction: so the record and the file commit together or not at all. A file whose statement after its own `commit` fails (a `notify`, say) stays recorded with what it committed, and the run goes red saying so.

- **The record decides what runs, so a file runs once and none is skipped.** A run that stops part way, or one GitHub cancels while it waits in the `run-migrations` concurrency group, is finished by the next run, whatever that push carries.
- **The first run begins the record.** Finding no record (no table, or an empty one), the runner applies 0197 before any other file, records every file that was on main before that push as run before the record began, without running any of them, and runs only the files the push added. So the push that first carries 0197 must merge only while the latest `run migrations` run on main is green: a file a red run skipped would otherwise be recorded as run when it was not. When the push before already holds 0197 but the record was never begun (its run was cancelled, the database could not be reached, 0197 failed, or the database was restored from before the record), the runner takes the files on main before the commit that brought 0197 instead, found by walking back along main's first parents, so the files that came with 0197 or after it are run, not recorded unrun. That walk relies on main moving only by merged pull requests, one commit each on its first-parent line; when it cannot find the commit, the run stops rather than guess. A restored database is handled this way only when its backup was taken after every file on main before 0197 had run; with an older backup the run goes green and records as run files whose changes the restored database does not hold, so after such a restore the record is begun by hand.
- **A failed migration stops the run and fails the workflow**: that file is rolled back and is not recorded, and the ones after it are not run. The next run applies it and then them.
- **A migration that failed has never run, so it is corrected in place** in a new pull request, and the next deploy runs it. **A migration that has run is never edited**: its correction is a new file. **A migration on the record is never renamed** either: the record goes by name, so a renamed file is run again. The rehearsal and the data-loss check read a renamed file as one added under its new name. A recorded file whose contents have changed since it ran is named in a warning on every run and never run again.
- **The runner prints the live Postgres version**, and warns when its major version differs from the rehearsal's (`scripts/migrations/rehearsal-postgres.sh`).
- **The connection is the repository secret `SUPABASE_DB_URL`** (the Session pooler string). When a push adds a migration and the secret is not set, the workflow fails and says so, so nobody takes it for run. A push with no migration passes whether or not the secret is set.
- **No one is at the keyboard when a migration runs, so it protects the data already there.** Additive (`create table if not exists`, `add column if not exists`), safe to run twice, never dropping or rewriting a table, column or row that holds data in use. The database backups are the safety net, not the plan.
- **The record says what ran.** An administrator's Claude reads it through read_data_inventory: the files run before the record began, the files the deploy has applied, the file that failed in the latest run and the files waiting for the next. A red run is still the one thing to act on.
- **Every table's rows are counted around the run.** Before the first migration and after the last, the run counts the rows of every table in the public schema (`scripts/migrations/count-every-table.sql`) and keeps both readings in `data_inventories`, one row each, sharing the run's `migration_run_id`. It counts rows and never reads what a row holds. When any table has fewer rows after than before, a table that is gone counting as empty, the run goes red naming each table and by how many; the readings are kept either way. A table the live site empties in the seconds the run takes would show the same, so a red count is looked into before anything else merges. An administrator's Claude reads the latest reading and the one before it through the connector's read_data_inventory action, which only administrators are offered.
- **A migration that would take away data is refused before it merges.** *Run test suite* reads every migration file a pull request adds or changes (`scripts/migrations/check-added-migrations.mjs`, rules in `src/lib/server/migrations/`) and fails when one drops or renames a table or a column, empties a table, deletes rows, or drops a type or domain with cascade, naming the file, the line and the statement. Statements inside a `do` block count; a function's body does not, since defining it runs nothing. The answer is a new table or column beside the old one with the rows copied in, never moved. A merged file is read again only when a pull request changes it.

## Every waiting migration is rehearsed before it merges

Reading a migration's words is not running it, so *Run test suite* also rehearses the next deploy on a scratch database, and the live deploy is never the first time a migration runs. On a pull request that adds or changes a migration, the runner, anything in `scripts/migrations/`, `docs/sql/base-schema.sql`, `docs/sql/fix-everything.sql` or `.github/workflows/ci.yml`, four steps run inside that required job, so no ruleset has to change:

1. `scripts/migrations/start-scratch-postgres.sh` starts a throwaway Postgres in a container, listening on 127.0.0.1 alone. Its major version is stated in `scripts/migrations/rehearsal-postgres.sh` and nowhere else.
2. `scripts/migrations/build-stand-in-database.sh` builds a stand-in for the live database as it is at the default branch: Supabase's own roles and the parts of `auth` and `storage` the migrations name (`scripts/migrations/supabase-stand-ins.sql`, which holds only what Supabase really has), then the two base schema files, then every `migrations/*.sql` file on the default branch in the runner's order. That history was run by hand before the workflow existed and a few files name columns renamed later, so this replay forgives: a statement that fails is skipped, and the whole history is replayed twice.
3. `scripts/migrations/rehearse-added-migrations.sh` runs the deploy's own runner, `scripts/run-added-migrations.sh`, from the default branch's commit to the pull request's merge commit — every file the next deploy would run, in file-name order, which matters because numbers merge out of order — and then runs the same files again on the same database, taking them off the stand-in's record first so the second run applies them again. Once the record is on the default branch, the stand-in's record holds every file there except the ones the pull request changes, as the live record would after a file failed and was corrected in place; until then the first run rehearses beginning the record.
4. `scripts/migrations/prove-migration-record.sh` proves the record on invented files that carry their own `begin` and `commit`, in a throwaway repository: a first run with no record in which each file is recorded exactly when it applied and the third, failing part way, leaves no record and none of its changes; a run stopped while the fourth file runs, finished by the next without running any file twice; a recorded file that was edited, named in a warning and not run; and a file that fails after its own commit, kept on the record and not run again. `scripts/migrations/prove-first-run-that-never-began.sh` proves that when the push bringing 0197 and two files never began the record (once not run at all, once stopped after 0197 applied with the record empty), the next push's run records only the files on main before 0197 came and runs the first push's files and its own, in order.

The step is red when a file fails, when a second run fails after the first ran clean (the file is not safe to run twice), when a table has fewer rows after a run than before, or when a run kept no row counts in `data_inventories`, so a change that takes the counting out of the runner goes red too. On a pull request into `staging` the base of the rehearsal is still the default branch, so it runs everything `staging` holds ahead of it plus this pull request's files; on the promotion pull request the base is the default branch itself, so the promotion rehearses the real deploy. When the next deploy would run no file, the rehearsal says so and passes. To run it by hand, from a checkout of the commit the deploy would take: `./scripts/migrations/start-scratch-postgres.sh`, then `SCRATCH_SERVER_URL=postgresql://postgres@127.0.0.1:54329 ./scripts/migrations/rehearse-added-migrations.sh <default branch's commit>`.

What it proves is the SQL, the order and the runner's flow. What it does not prove:

- **What live rows do.** The scratch database holds no client data, and nothing from production is ever copied into it; it never connects to the live database and reads no secret. A migration that copies rows, deletes through a function or guards a record with triggers is still tried by hand on invented rows when its rows matter.
- **Supabase's permissions.** The scratch server runs migrations as a true superuser, which Supabase's `postgres` role is not, so a statement that needs a superuser passes here and fails live.
- **The live shape exactly.** The stand-in is built from the files, not copied from the live schema, so it is close to it, not a copy of it.

**Never run the project-process kit's bootstrap here with `--with-migration-run`.** It would replace `scripts/run-added-migrations.sh` and `.github/workflows/run-migrations.yml` with the kit's copies, which neither count rows nor keep the record of applied migrations, and the rehearsal would then go red on every migration for keeping no row counts.

## The site stands before its migration runs

A pull request merges by itself when CI passes; Vercel deploys main and the run migrations workflow runs its migration at the same time, so the two race and the new code may run against the old schema for a while — or for good, if the migration fails. So a pull request whose migration adds a table, a column or a relationship ships code that stands without it:

- **Every reader of the new schema on a path every request runs** — a layout load, a hook, the connector's account standing — answers empty when the schema is not there yet: `if (isSchemaNotYetMigrated(error)) return <empty>;` before the `throw`, from `$lib/server/schema/schemaNotYetMigrated`. Readers behind a page of their own may fail until the migration runs; the connector already tells the caller a migration is missing.
- **Writes are not guarded.** A write to a table that does not exist yet fails and says so; it is never quietly dropped.
- **Nothing live code reads is dropped or renamed.** A rename is a new table or column beside the old one, with the rows copied in and the code moved over to it; the old one stays where it is, unread, because CI refuses a migration that drops or renames it.

## A project's staging branch deploys at its window

Where a project's repository has a `staging` branch, every pull request merges into it and deploys nothing. The project's *Deploy staging to main at* time (UK time, blank for no window; `update_project_details` takes it as `deployStagingAt`) is its deploy window: at that time each day the `deploy_windows` watch source compares `staging` with the default branch and, when staging is ahead, opens one pull request `DEPLOY: staging to <default>, <date>` with auto-merge on (reusing one already open). That merge is the day's deploy; the existing webhook counts it and marks the tasks done. Nothing to promote is recorded as such and skipped; a window that GitHub refused is tried again at the next knock and shows on the project header.

- **The cron door is knocked by `.github/workflows/deploy-windows.yml`**, every quarter hour, because Vercel's Hobby plan runs a cron once a day at most. It needs the repository secret `CRON_SECRET`, the same value as the Vercel variable; the knock never fails the workflow, so a door that answers 401 or 503 is a warning in its log, not a FIX task.
- **The site's `GITHUB_TOKEN` opens the pull requests**, so it needs pull request write on every project repository with a window. No per-repository secret.
- **Each day's window is one row of `project_deploy_windows`**, which is why a window runs once a day however often the door is knocked.
- **Deploy now promotes by hand, outside the window.** The Deploy now button on the project's Staged tab (and the connector's `deploy_staging_now`) runs the same promotion at once and keeps the run on `project_deploy_windows` as started by hand, a row of its own. It never takes the place of the day's timed window, which still runs at its time when `staging` has moved on again; the header shows the latest promotion of either kind.
- **Each promotion says what it carries.** The merge commits `staging` holds ahead of the default branch name the pull requests merged into it; each is matched to the task that recorded it (by pull request address, or by branch) and the promotion pull request body lists those tasks with links, and the pull requests no task recorded. The same lines are kept on the window record (`summary`), shown as the header fact's tooltip and by the connector's `read_project`.
- **A task knows where its merged work stands.** The merge of its pull request into `staging` sets `tasks.staged_at`; the merge of the promotion pull request (`staging` into the default branch) sets `tasks.live_at` on every staged task and tells each one it is live. The project page's *Staged, not live* panel lists the tasks between the two, latest merge first, so it is the list of what the next deploy carries; the task's branch panel, `read_task` and `read_project` say the same.
- **Each deploy says what it carried, after the fact.** A promotion's merge marks every task it carries live at one moment, so the tasks sharing a `live_at` are one deploy. The project page's *Live in each deploy* panel lists the last ten deploys, newest first, with the tasks each carried; *Deployment history* (`/projects/<id>/deploys`, from the Actions menu or the panel) holds every deploy, twenty to a page, searchable by task title and filtered by UK date. The connector's `read_deploy_history` answers the same, with the same words and dates, so anyone's Claude can say what went live last night or when something went live. Nothing new is stored: the history is read from `tasks.live_at`.
- **A pull request recorded after it merged is still recorded.** The webhook only hears a merge as it happens, so when `set_task_branch` is given a pull request address, the pull request is read from GitHub (`readMergedPullRequest`): one that has already merged is recorded as the webhook would have recorded it — done and staged, with GitHub's merged step on the lifecycle — and live as well when the default branch already holds its merge commit. An open pull request is left for the webhook; a task already staged or done is not recorded twice; and a GitHub refusal is reported in the action's answer, never a failure of it.

## Production deploys only from main

Vercel project `ybt` is connected to Your-Business-Today/YourBusinessToday with `main` as its production branch, so every merged pull request deploys production by itself. What is live is always what was merged, with its checks passed.

- **Production is never deployed by hand.** No `vercel --prod`, `vercel deploy --prod` or `vercel promote` of a local build: the CLI ships whatever the local checkout holds and goes around GitHub, its checks and the deploy count.
- **A fix ships by a merged pull request**, however small, and an urgent one is still a pull request that merges at green.
- **A rollback is Vercel's own.** Open the project's Deployments, pick an earlier `main` production deployment and use Instant Rollback, Promote or Redeploy on it; then fix forward with a pull request.
- **A pull request waits on its Vercel preview.** The preview is a required status check on `main`, so auto-merge does not fire while it builds or when it fails.

## The connector checks itself after every production deploy

The pipeline contract test proves in CI, against no database, that the connector still offers what the build pipeline calls. The `connector_self_check` watch source is the same check against the real thing: `.github/workflows/connector-self-check.yml` knocks on the cron door when Vercel reports a production deployment as successful (and on *Run workflow*), with the `CRON_SECRET` the deploy windows knock already uses, so it needs no setting of its own.

- **It compares the deployed connector with `src/lib/server/mcp/pipelineContract.json`**: the tools as the MCP layer lists them, and the actions as they are offered to an administrator, every promised name, input and value.
- **Then it runs reads against the live database** through the same MCP layer a client's Claude uses: the tools that only read, and a set of read actions through `run_read_action`, which refuses any action that writes, on the first project the administrator owns or is on. It never writes to a board; the only row it leaves is its own run in the watch run log.
- **A failure is red in GitHub.** The door answers 500 with the failures, one sentence each, and the workflow prints them and fails; a tool that failed says only what its caller would be told, and the cause is in the site's logs.
